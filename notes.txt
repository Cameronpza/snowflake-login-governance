A full record of how this project was built, start to finish.

1. Setup
Created project folder at `C:\Users\Cameron\work\repos\snowflake-login-governance`, matching GitHub repo created alongside it.
Signed up for a Snowflake free trial account. Account identifier: `vl30231.af-south-1.aws` (AWS, af-south-1/Cape Town region). $400 trial credit, 30-day trial.
Created two test users (`testuser1`, `testuser2`) and generated real login activity by logging in/out multiple times, including deliberate wrong-password attempts.
Accidentally triggered a real Snowflake security feature: 5 failed login attempts locks an account for 15 minutes. Unlocked manually with `ALTER USER testuser2 SET MINS_TO_UNLOCK = 0;`. Good real-world proof-of-concept for the "repeated failed logins" detection this project is built around.
2. The MCP Journey — Three Attempts, Three Genuine Blockers
The original goal was to connect Claude Code to Snowflake via MCP (Model Context Protocol), so Claude Code could query real data conversationally while building.
Attempt 1 — Snowflake's own managed MCP server
Created successfully via SQL (`CREATE MCP SERVER ... FROM SPECIFICATION`), scoped to read-only SQL execution.
Generated a Programmatic Access Token (PAT) to connect it.
Hit a network policy requirement (Snowflake error 390432) — fixed by creating a network policy (`ALLOWED_IP_LIST = ('0.0.0.0/0')`) and applying it account-wide. Noted trade-off: allowing all IPs is acceptable for a personal dev account, would be scoped tighter in production.
Still failed with "Access denied for trial accounts" (error 399504) — confirmed via research that Snowflake's managed MCP server requires a paid account tier, not available on trial accounts at all. Genuine platform restriction, not fixable.
Attempt 2 — Open-source alternative (`dynamike/snowflake-mcp-server`)
Cloned into `C:\Users\Cameron\work\sandbox\snowflake-mcp-server` (kept separate from own project code, per the repos/sandbox folder convention).
Failed to build: `cffi` package couldn't compile on Python 3.14 (too new — missing Microsoft C++ Build Tools).
Fixed by pinning the tool's virtual environment to Python 3.12 instead (`uv python install 3.12`, `uv venv --python 3.12`), without touching the main system Python install.
Attempt 3 — Same tool, now running, external-browser auth
Connected to Claude Code via `claude mcp add` with a local stdio command.
Timed out after 30 seconds — external-browser SSO login needs a human to complete it interactively, but Claude Code's MCP connection attempt doesn't wait long enough for that.
Decision: after diagnosing all three failures individually (not just giving up), dropped MCP for the Snowflake connection specifically. Connected via the Snowflake Python connector directly instead. Removed the broken `snowflake-read` MCP registration from Claude Code (`claude mcp remove`).
3. Connecting Directly (Python Connector)
Initial attempts used the personal Snowflake login (`CamZA`), which turned out to be SSO-only (no traditional password) — couldn't be used for direct password-based scripts.
Created a dedicated service account instead (`claude_service_user`) with proper password authentication — standard practice: keep personal SSO login separate from service/automation credentials.
Credentials stored in a local `.env` file (gitignored); `.env.example` committed as a template with placeholder values only.
Several rounds of `.env` not saving correctly through the VS Code editor — eventually fixed by overwriting the file directly via a PowerShell heredoc command for a clean, deterministic write.
First successful connection confirmed: session info, databases, warehouses, roles, and users all queried successfully via the direct Python connector.
4. The Security Fix — Least-Privilege Role
The problem found: `claude_service_user` had been given full `ACCOUNTADMIN` access — far more than needed just to read login history. Flagged as ironic in a project specifically about login governance.
The fix:
Created a new role, `LOGIN_GOVERNANCE_READER`, using Snowflake's built-in `SNOWFLAKE.SECURITY_VIEWER` database role — scoped to security-relevant views only (LOGIN_HISTORY, USERS, GRANTS_TO_USERS, etc.), not the entire ACCOUNT_USAGE schema.
Granted only `USAGE` on the warehouse (enough to run queries, not manage it).
Granted the new role to `claude_service_user`, set it as the default role, and revoked `ACCOUNTADMIN` entirely.
Built as an idempotent script (`setup_service_role.py`), safe to re-run.
Verification (not just assumed):
Confirmed `CURRENT_ROLE()` showed `LOGIN_GOVERNANCE_READER` after the change.
Confirmed `LOGIN_HISTORY` queries still worked under the restricted role.
Deliberately tried `USE ROLE ACCOUNTADMIN` afterward and confirmed it correctly failed — proving the downgrade actually took effect, not just switched at the session level.
5. Planning the Dashboard (PRD)
Had Claude Code explore the real data first, before designing any detection logic. Findings from real `LOGIN_HISTORY` data (39 rows initially, later grown to 99):
Only 4 users active (1 real personal account, 2 test accounts, 1 service account), effectively 1 source IP.
Repeated failed logins — well supported by real data. Genuine failure bursts existed (from the earlier lockout testing), including Snowflake's own `USER_LOCKED_TEMP` and `OVERFLOW_FAILURE_EVENTS_ELIDED` markers.
Weak auth / MFA — `SECOND_AUTHENTICATION_FACTOR` was null on every single row (0% MFA usage account-wide). Decision: no baseline exists to detect a deviation from, so this became a standing compliance tile (MFA usage rate) rather than an anomaly detector — more honest than forcing a fake signal.
Odd-hour logins — only 4 active calendar days, heavily weekend/test-skewed. Decision: use a simple, static business-hours window (08:00–18:00, timezone-configurable) rather than a per-user learned baseline, which the data was too thin to support honestly.
PRD written to `PRD.md`, decisions recorded, marked "Ready to build" once all three open questions were resolved.
6. Building
`SQL/01–05` — exploration queries (schema, users/auth, failures, odd hours, login details/connection info) — used to inform the PRD.
`SQL/06_repeated_failed_logins.sql` — sliding-window burst detection (N failures in T minutes) plus automatic escalation flags for Snowflake's own lockout/overflow events.
`SQL/07_mfa_compliance.sql` — overall + per-user MFA compliance rate, plus a separate tile for programmatic access token (PAT) logins.
`SQL/08_odd_hours.sql` — static business-hours window. Caught and fixed a real bug along the way: unconverted `HOUR()` was silently using session-local time instead of UTC — fixed with explicit `CONVERT_TIMEZONE`.
`app.py` — Streamlit dashboard, same header/count/table layout as the first project. Sidebar exposes the PRD's open config questions (excluded accounts, timezone/window, failure threshold) as live-tunable controls rather than hardcoded values.
7. Review and Security
`/ultrareview` (multi-agent cloud review) run before first push — found and fixed 4 real bugs: leaked real account/username values in `.env.example`, a "bootstrap trap" where a partial failure in the role-setup script could strand the service account with no valid role, a hardcoded warehouse name instead of using the configured one, and missing `try/finally` connection cleanup on failure.
`/security-review` (full codebase) — no HIGH or MEDIUM confidence findings. Confirmed: all dynamic SQL values use proper parameterized binding (no injection risk), `.env` genuinely untracked by Git, no unsafe HTML rendering, `setup_service_role.py` reduces privilege rather than introducing an escalation path.
